## Explicit rules and known gaps

- Policy `schema_version == 1`, non-empty origins and uniqueness are not supplied by Typify/Serde alone. Collector currently gets origin cardinality, regex, uniqueness and unknown-field rejection from the startup-built Schema validator; its parser checks version and row identity. These remain independently asserted in consumer tests so generated structure success is not treated as full validation.
- Capabilities identity, storage version, required Page Views and dependencies are consumer semantics. Unknown fields and fixed privacy constants are Schema/Serde boundary behavior; fixtures should keep testing them through the runtime.
- Update Origin normalization, dependencies, duplicate definition IDs, privacy field filtering and HTTP error mapping are service semantics, not type constraints. Keep their outcome assertions in Analytics API tests.
- TypeScript types are not runtime parsers. Positive and `@ts-expect-error` probes establish static shape only. Schema fixtures and Rust/HTTP consumers establish runtime behavior.
- Policy `version` and `rate_limit_per_minute` have no Schema upper bound, while Collector and PostgreSQL BIGINT paths are signed 64-bit. Values above `i64::MAX` are an implementation-range exception; this report does not tighten Schema or claim full parity. JavaScript `number` also cannot represent every large JSON integer exactly.
- Definition revisions have no direct stored-document Schema. The update contract and Processor import path are separate inputs with server-managed revision metadata; parity is limited to shared semantic expectations and currently named fixtures.

## Date-time compatibility gate

The strict candidates are policy `/updated_at`, every `/ingest_keys/*/created_at`, and capability `/updated_at`. The read-only preflight covers both `site_environment_policies` and `site_capability_configurations`; its `--fixtures` mode exercises all date-time candidates. On 2026-09-30 the audit ran against the only active environment, local-development Compose PostgreSQL: 1 policy document and 7 capability documents were audited, with 0 invalid date-time fields. Strict format assertions are now enabled in Collector, `configuration-runtime`, and Analytics API stored-document validators. Preserve last-good/stale behavior for invalid stored policy documents. Before deploying this strict build to any future environment with existing data, run the same database preflight there and remediate findings first.

Canonical candidates:

- `environment-policy/invalid/invalid-updated-at-date-time.json`
- `environment-policy/invalid/invalid-key-created-at-date-time.json`
- `capabilities/invalid/invalid-updated-at-date-time.json`

Run `node scripts/audit-policy-datetimes.mjs --fixtures` to check both stored document types; run the same command without arguments with the target environment `DATABASE_URL` for the read-only database audit. The candidate Schema outcomes are exercised by `node scripts/check-configuration-contract-parity.mjs`; production acceptance is governed by strict-format assertions in the stored-document consumers.
