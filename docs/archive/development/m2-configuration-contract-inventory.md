## M2 migration order

1. **Stored Environment Policy:** establish the stored model and explicit rules, reuse the Collector validator, and migrate policy create/update/key operations with that model. Complete the per-deployment date-time preflight before enabling format assertion.
2. **Stored Site Capabilities and registry:** establish the registry source of truth and drift check, then migrate runtime snapshots and the capability update API together.
3. **Definition revisions:** define the stored revision model, then migrate definition update APIs and Processor's legacy import path together; preserve the import-only behavior and record its distinct validation path.

This is the planned dependency order, not a statement that the later slices are implemented.

## Stored document read validation

The current Analytics API GET paths return or construct responses from database `serde_json::Value` without running the stored-document Schema validator. Collector policy refresh and `CapabilityRuntime` do validate stored documents before applying runtime snapshots. Processor's definition import validates its source with `AnalyticsDefinitions::load`/`validate`; its database read deserializes to the typed model but does not call semantic validation. M2 must decide whether each read path validates on load or relies on the database constraints plus prior validated writes, and test that boundary explicitly.

## Explicit exclusions

- `audit-event.schema.json` describes audit records, not configuration documents or update requests; its lifecycle is not part of M2.1's configuration model inventory.
- Site Registry identity, foreign keys, legacy backfill and migration tooling remain M3.
- New Site create/list/detail contracts remain M5.
- Event wire types and Collector event validation remain M9.

## Date-time compatibility decision

ADR-017 selects Schema-strict behavior for stored policy `updated_at` and `ingest_keys[].created_at`. M0b fixtures `invalid-updated-at-date-time.json` and `invalid-key-created-at-date-time.json` show that Collector currently accepts values the Schema rejects because the policy validator does not enable format assertions. Before M2.2 enables format assertions, operators must set `DATABASE_URL` to each target database and run the read-only preflight `node scripts/audit-policy-datetimes.mjs`; the script fails closed when the URL is missing or has no database name, and requires one explicit hostname, selects a writable primary, and clears inherited libpq routing variables so they cannot redirect the connection; it resolves the visible environment policy table and schema through PostgreSQL catalogs, verifies its kind and expected identity/document columns, and safely quotes the schema before reading; it clears inherited `PGOPTIONS` and rejects URL `options` and `target_session_attrs`. Repair any reported records through the supported configuration write path. Repairing `updated_at` requires a policy update that writes a new server timestamp; repairing an invalid key `created_at` requires revoking that key and creating a replacement, with the associated key-rotation impact reviewed by the operator. The script reports identities and JSON field paths, not timestamp values, and uses read-only transactions for relation resolution and data inspection. It requires `DATABASE_URL` to name the intended target database; credentials should be supplied through the deployment secret/environment mechanism, not committed to the repository. `node scripts/audit-policy-datetimes.mjs --fixtures` checks its date-time logic against the canonical valid and invalid fixtures without connecting to a database.

The PostgreSQL predicate was also exercised against a disposable PostgreSQL 18.6 instance. It accepts `2026-09-29T24:00:00Z`, which the repository JSON Schema validator rejects; this confirms a real database-accepted / Schema-invalid gap and justifies an explicit preflight before strict Schema validation is enabled. PostgreSQL also accepts `2026-09-29T23:59:60Z`, which the repository JSON Schema validator accepts, so it is not a parity gap. This local check did not inspect any deployment database.

Once strict validation is enabled, a malformed database document follows the existing failure behavior: the Collector marks that policy stale and retains its last-good policy; if no last-good value exists, the invalid policy is not applied. The M2.1 decision does not enable strict validation or alter API writes.
