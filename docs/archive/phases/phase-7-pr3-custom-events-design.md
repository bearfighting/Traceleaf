# Phase 7 PR3 Design — Custom Events

> Status: Implemented; review fixes applied. Full PR3 verification is tracked in the project checks.
> Scope: Protocol, Browser SDK, Collector, raw storage, Processor, Analytics API, Dashboard and end-to-end acceptance for site-scoped custom events.

## 1. Goal and boundaries

Allow a site to record bounded product actions such as `signup_started` or `purchase_completed`, then report event counts. Custom Events are independent of Page Views: recording one does not create a Page View or affect Visitor, Session, Page View or Browser Dimension metrics.

This PR adds a fixed event contract and a basic count workflow. It does not add user-defined event schemas, capability configuration UI, arbitrary property filtering/querying, Conversion/Funnel, Web Vitals, or identity beyond the existing optional anonymous `visitor_id`. Dashboard configuration remains Phase 8 work.

## 2. Event Protocol contract

Custom Events use the existing Event Protocol `schema_version: 1` and Event Batch envelope. A batch may contain Page Views and Custom Events together, subject to existing batch count and request byte limits, but every event in one batch must have the same `site_id` (the current Collector authorization and rate-limit boundary). The Collector authorizes that site once and rejects mixed-site batches; it rejects the batch atomically if any event is invalid or unauthorized.

Canonical event shape:

```json
{
  "schema_version": 1,
  "event_id": "01J00000000000000000000001",
  "type": "custom_event",
  "site_id": "site_example",
  "occurred_at": 1760000000000,
  "event_name": "purchase_completed",
  "properties": {"plan": "pro", "amount": 24.5},
  "visitor_id": "11111111-1111-4111-8111-111111111111"
}
```

| Field | Required | Contract |
| --- | --- | --- |
| `schema_version` | yes | Integer `1`, same meaning as current protocol. |
| `event_id` | yes | Canonical 26-character ULID; idempotency key is `(site_id, event_id)`. |
| `type` | yes | Exact string `custom_event`. |
| `site_id` | yes | Existing site ID syntax and authorization rules. |
| `occurred_at` | yes | Non-negative Unix milliseconds; Collector applies the existing five-minute future limit. |
| `event_name` | yes | 1–64 ASCII characters, starts with a letter, then letters, digits, `_`, `.`, or `-`; case-sensitive. |
| `properties` | yes | JSON object; `{}` is valid. Rules below. |
| `visitor_id` | no | Existing canonical site-scoped anonymous UUID v4. Never generated by the server as a fallback. |

Custom Events do not accept Page View-only fields (`path`, `url`, `title`, `referrer`, `context`, `context_schema_version`) or client-provided `session_id`. Unknown top-level fields are rejected for this event type. Page View's existing forward-compatible unknown-field policy remains unchanged. `visitor_id` is optional and does not change Custom Event counting or require an identity.

### Property limits and privacy

`properties` is validated recursively before persistence:

- JSON values: string, boolean, finite number, null, array, or object; no non-JSON values.
- At most 32 keys total across all objects; object keys are 1–64 ASCII characters matching `[A-Za-z][A-Za-z0-9_.-]*`.
- At most 4 nested object/array levels below `properties`.
- Arrays contain at most 20 items each.
- Strings are at most 256 UTF-8 bytes each.
- Compact UTF-8 JSON encoding of the complete `properties` object is at most 8 KiB.
- Reject non-finite numbers, exceeded bounds, and case-insensitive direct-identifier/authentication keys after removing `_`, `-`, and `.` separators: `email`, `emailaddress`, `useremail`, `phone`, `phonenumber`, `name`, `firstname`, `lastname`, `fullname`, `address`, `homeaddress`, `streetaddress`, `ip`, `ipaddress`, `useragent`, `cookie`, `password`, `passwd`, `token`, `userid`, or `useridentifier`. Other keys such as `product_name` remain valid.

These rules bound storage and reject obvious sensitive fields; they cannot detect sensitive values hidden under innocuous keys. SDK documentation must tell integrators to send only low-risk business attributes and never personal, authentication, payment-card, raw IP or raw User-Agent data. Collector does not attempt content classification or silently redact values. Invalid properties reject the event with a stable validation error; they are never truncated or partially accepted.

### Time, duplicates and batch behavior

- The SDK assigns `event_id` and `occurred_at` when `event()` is called, using the existing event ID source and clock injection patterns.
- `received_at` is assigned by the Collector after successful validation. It is server-owned and not accepted from the client.
- Event counts and date buckets use `occurred_at` in UTC. `received_at` supports freshness and processing diagnostics only.
- A duplicate `(site_id, event_id)` is acknowledged by the existing accepted-batch response but does not add or overwrite a raw row, fact, or count. Reusing the same ID with a different payload leaves the first stored payload unchanged; no separate duplicate response is introduced.
- A structurally invalid or unauthorized event rejects the whole batch, preserving current ingestion atomicity. A valid duplicate mixed with new valid events does not reject the batch. Mixed-site batches are rejected before storage.
- Existing late-event/raw-event policy applies. Any accepted event is retained; Processor must be able to rebuild derived facts from `raw_events`.

## 3. SDK contract

Add `analytics.event(name, properties?)` to `Analytics`. The method is a no-op unless consent is granted or after destroy. If name or properties fail SDK-side validation, it drops the event and reports a `TypeError` through the existing `onError` callback; it does not throw through the application call site. The SDK creates a Custom Event, applies `beforeSend`, then enqueues it into the existing bounded buffer and transport. `beforeSend` may return `null` to drop it; it may not change `schema_version`, `type`, `event_id`, or `site_id`. The SDK validates event name and property bounds locally for useful feedback, while Collector validation remains authoritative.

`event()` returns `void`, matching `pageview()`. Buffering, flush, transport failure, consent revocation and batch behavior are shared with Page Views. `visitor_id` is attached only when the existing visitor store contains a valid ID and consent is granted. The Browser SDK does not infer a `path` or include Browser Context in a Custom Event.

## 4. Collector and persistence

Protocol TS/Rust types become a discriminated event union; the batch remains a single ordered `events` array. Collector validates the event-specific schema and property limits, checks site/Origin/Public Ingest Key using existing policy, applies existing rate/payload limits, timestamps `received_at`, and writes accepted events via the existing idempotent storage boundary.

`raw_events` remains the source of truth. Add a migration that permits `path` to be null for non-Page-View events; Page View writes continue to require a valid path in protocol and processor validation. Custom Event envelope and properties are retained in `payload`; do not duplicate raw property keys into dedicated columns. Existing `(site_id, event_id)` uniqueness remains the idempotency boundary. Existing Page View rows and query semantics remain unchanged.

Migration and ingestion changes must be additive and compatible with stored rows. Page View aggregation must explicitly filter `event_type = 'page_view'`; Custom Events must never reach Page View normalization, totals, routes, visitor/session or dimension processors as if they were Page Views.

## 5. Processing and rebuild semantics

Create one derived `custom_event_facts` row per accepted Custom Event, uniquely keyed by `(site_id, event_id)`, containing `occurred_at`, `received_at`, and `event_name`. Facts are derived from `raw_events`; a reprocess/upsert for a duplicate event is idempotent. The original `properties` remain only in `raw_events.payload`; PR3 does not create property-level indexes or expose properties through reports.

Provide an explicit rebuild path for Custom Event facts from raw rows. Incremental processing and rebuild must yield the same rows/counts. Counts group by site, UTC date of `occurred_at`, and exact case-sensitive `event_name`. No cross-site aggregation is allowed. Late events update the affected date/event count when processed; response freshness derives from existing processed-watermark semantics.

## 6. Analytics API and Dashboard

Add a site-scoped report endpoint following existing report conventions:

```text
GET /v1/sites/{site_id}/reports/{from}/{to}/events
```

Return bounded aggregate rows by event name and UTC date, overall total, date range, and `data_as_of`/freshness metadata using existing API conventions. Query rules: inclusive date range, existing maximum date-range and pagination limits, deterministic ordering (`event_name`, then date), and no properties or Visitor IDs in the response. Optional `event_name` exact-match filter is supported; no free-form property filter. Empty range returns success with total zero and an empty row list. Invalid date/filter input uses the established API validation error format. Requests are always site-scoped and cannot reveal other site data.

Dashboard adds an Events report with a date range, total event count and event-name/date table. It shows loading, empty, and API error states using existing dashboard patterns. Event names are displayed as data, not interpreted as markup. Event properties are not displayed. No event definition editor or toggle is added.

## 7. Canonical contract resources and fixtures

Before implementation, add the Custom Event schema to canonical `protocol/events/schemas/` and update the batch schema so items accept the event union. Update `docs/event-protocol.md`, generated/hand-maintained TypeScript and Rust types, examples, HTTP contract fixtures, and validators together.

Required fixtures:

- valid single Custom Event with empty properties;
- valid event with bounded nested properties and optional visitor ID;
- mixed Page View/Custom Event batch;
- invalid event name and missing required fields;
- each JSON type accepted, plus invalid non-object root and invalid/non-finite values where representable;
- depth, total-key, array-length, string-byte, and total-byte limit boundaries and one-over cases;
- rejected sensitive-key variants;
- unknown top-level field and forbidden Page View/session fields;
- duplicate IDs, including same-site duplicate, same ID on different sites, and mixed-site batch rejection;
- invalid-batch atomicity and site authorization isolation;
- late event and UTC date-boundary cases;
- API empty range, multiple event names/dates, exact-name filter and site isolation.

Fixtures should include exact expected error codes/reasons where the existing HTTP fixture format supports them. Keep one canonical contract namespace; do not create a protocol v2 directory.

## 8. Implementation order and acceptance

1. Land schema/types/examples/fixtures and validator support; run protocol and HTTP contract validation.
2. Implement SDK `event()` and unit/integration tests against mock transport.
3. Implement Collector validation and ingestion integration tests, including privacy bounds and idempotency.
4. Add migration, raw-event persistence behavior, Processor facts/rebuild and database tests.
5. Add API contract/query tests and Dashboard report states.
6. Add full SDK → Collector → PostgreSQL → Processor → Analytics API → Dashboard E2E.
7. Run existing protocol, unit, integration, analytics E2E and dashboard E2E regressions.

PR3 is complete only when mixed batches work end to end, invalid input is rejected without partial acceptance, duplicate delivery is idempotent, rebuild matches incremental processing, reports are site-isolated and property-safe, and Page View metrics/contracts remain unchanged.

## 9. Explicit exclusions and follow-up

- Conversion/Funnel can use exact `event_name` and approved properties in a later PR; this PR does not define their identity/window rules.
- No event schema registry, user-authored validation rules, property-based query API, automatic PII classifier, IP-derived data, or arbitrary retention policy.
- A future change to property limits, sensitive-key policy, event-name matching or API response shape requires explicit contract review and fixtures; breaking changes require a new public protocol/API version.
