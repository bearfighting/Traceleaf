# Commands and E2E Baseline Inventory

> Archived: implementation and measurements are historical evidence. For current commands, inspect the root `package.json` and [Getting Started](../../getting-started.md); deferred project work is tracked in [Project Status](../../project-status.md).

Command implementations now live by responsibility in `tooling/`, `db/` and `tests/e2e/`. `package.json` invokes those implementations directly; historical measurements below retain the paths used when they were recorded.

## Baseline status and scope

This inventory was prepared before the scripts/E2E tooling refactor. Its baseline runs used PID-scoped Compose projects and PostgreSQL volumes, which were cleaned up on exit.

The requested representative suites are `analytics` (`pnpm e2e:analytics`), `dashboard` (`pnpm e2e:dashboard`) and `dev-startup` (`pnpm e2e:dev-startup`). “Cold” means that the suite's E2E named volumes are new or empty. Docker daemon image and build layer caches stay intact. “Warm” means rerunning the same suite against the same E2E named volumes. This is not a no-cache Docker build.

### Responsibilities that may overlap

- `tests/e2e/support/e2e-compose.mjs` centralizes Compose argument construction, environment merging, output capture/error handling, the shared one-shot migration command and project removal for Compose-backed E2E suites. Browser/process cleanup, service startup order (including suites that reach migration through Compose dependencies), diagnostics and scenario seed data remain local because their lifecycles differ. Dashboard still includes analytics flows, so some fixture/data setup overlaps the Analytics suite.
- Capability seed SQL is shared by Analytics, Dashboard and Configuration; direct ingest-policy seeding is shared by Analytics and Dashboard. Configuration and Site Management also exercise policy/configuration creation through the management API. Development seed intentionally creates the fixed `site_example`, while E2E fixtures use disposable scenario data.
- `test:migrations` exercises clean/current/upgrade histories, while `test:integration` migrates the current configured database and runs application-level PostgreSQL tests. Their migration invocation overlaps, while their assertions differ.
- E2E projects are isolated, but E2E external cache volumes are shared by prefix and scope. `dashboard_next` is suite scoped; the other cache volumes are shared across suites that use the same prefix. Do not run cold cleanup against active tests.
- CI E2E jobs are separate runners, so they cannot share named volumes with one another. Some have measurement wrapper and upload artifacts; router adapter / router Compose jobs do not.

## Reproducible cold/warm measurement procedure

Run only after the project status gate is satisfied. Use a clean worktree at a recorded commit, a quiet host, and a running Docker daemon. Do not run the three pairs in parallel; each pair deliberately reuses cache volumes and host image/build cache.

1. Record `git rev-parse HEAD`, `git status --short`, OS/kernel/architecture, Docker Engine and Compose versions, Node, pnpm and Rust versions, and the exact command. Record whether package install and Playwright installation were already complete. Keep the Docker daemon and its build cache intact for all six runs.
2. Record the current `tests/e2e/support/e2e-cache.mjs` input list and calculate the exact prefix using the script's behavior: SHA-256 over resolved repository path followed by each relative path and file bytes, truncated to 12 hex characters and prefixed `web-analytics-e2e-`. This matters because a separate checkout path selects a different cache family.
3. For each scope `analytics`, `dashboard`, `dev-startup`, inspect only that prefix's E2E volumes. Before the cold run, remove the seven scope-relevant volumes named by `prepareE2ECaches` (`collector_target`, `processor_target`, `analytics_api_target`, `cargo_home`, `root_node_modules`, `dashboard_node_modules`, and `<scope>_dashboard_next`) if they already exist. Confirm that no running Compose project uses them. This removes only E2E dependency/build volumes; it does not remove Docker images/build cache. Then run the command once, save stdout/stderr and start/end times, and label this run `cold E2E volumes / warm-or-existing Docker daemon cache`.
4. Without deleting volumes, run the same command again with identical environment and label it `warm E2E volumes / same Docker daemon cache`.
5. Archive each run's `artifacts/ci-docker-cache/<suite>/measurement.json` and `e2e-build.log` when the wrapper is used. Also capture `docker system df -v`, `docker image ls` for involved images, `docker volume ls` / `docker volume inspect`, Compose `ps`, and Compose build output. Record image IDs/sizes and before/after volume sizes. Obtain build, startup, migration and test durations from timestamped plain Compose logs; if a boundary cannot be extracted robustly, record `unavailable` and explain why rather than estimate silently.
6. Repeat steps 3–5 independently per scope. Do not run a development seed; `e2e:dev-startup` tests the seed in its isolated E2E database.

For every run, record: commit; host/tool versions; exact command/environment; suite and cold/warm condition; wall time and exit status; per-image build result/duration and image size; container readiness/startup time; migration time; test time; volume sizes before/after; available dependency/download byte count; and runner ingress delta. Mark unsupported values unavailable. Runner `rx_bytes` is a host-interface approximation that can include unrelated traffic, registry responses, package traffic and other background downloads; describe it as an upper-bound-like ambient measurement, not exact Docker network usage. Docker build output may show layer cache hits but does not on its own measure transferred bytes.
