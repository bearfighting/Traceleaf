# M0b 第四步：样本约束与运行时责任清单

- 日期：2026-09-29
- 范围：Event Batch V1（Page View、Custom Event、Web Vital、Browser Context）及 Stored Environment Policy V1。
- 目的：逐项区分 JSON Schema 的结构约束、静态类型表达、运行时校验责任和现有证据。生成类型是评估样本，不是生产类型或运行时验证器。
- Schema 入口：`protocol/events/schemas/event-batch.schema.json`、`protocol/contracts/configuration/current/environment-policy.schema.json`。

## 判读约定

- **TS 当前**指 `packages/protocol-ts` 手工维护的事件类型；存储 policy 尚无专属 TS wire 类型。
- **json2ts** 指 `json-schema-to-typescript` 样本；事件和 policy 均有产物。
- **typify** 指配置 Rust 生成样本；事件 Rust 无产物。
- **Toolkit** 仅有配置 TS 样本。该样本可编译但将 wire snake_case 字段转成 camelCase，因此不能直接代表 wire JSON。
- “静态类型表达”只描述编译期形状，不表示从不可信 JSON 解析时执行了约束。

## Schema 外语义与系统边界

| 规则                                                                    | 是否由单份 Schema / 静态类型保证               | 运行时责任 / 证据                                                                                                                   | 覆盖与后续 parity 缺口                                                                                            |
| ----------------------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 同一存储策略文档必须与数据库行 `site_id`、`environment`、`version` 一致 | 否；这是文档与数据库元数据的关系               | `runtime_policy.rs::parse_database_policy` 检查身份/版本；`rejects_database_identity_and_version_mismatches` 单元测试覆盖           | 有单元测试，canonical policy fixture 逐例测试不覆盖数据库行绑定。第六步应将此类语义用例与纯 Schema fixture 分开。 |
| 多策略合并后的 Origin 冲突（含规范化后的等价 Origin）                   | 否；跨文档且依赖规范化/注册上下文              | `SiteRegistry::from_runtime_sites` 与 config registry 负责冲突处理；`services/collector/src/config.rs` 有重复 Origin/跨环境冲突测试 | 运行时已有定向测试；不属于单 policy Schema parity。                                                               |
| 空 ingest keys 对 enabled/disabled 策略的运行时可用状态                 | Schema 只允许结构，不表达策略运行状态          | `runtime_policy.rs` 刷新/注册时处理；`empty-ingest-keys.json` 有 runtime policy 测试                                                | 基线和 runtime_policy 定向测试覆盖；需要在报告中避免将运行态规则说成 Schema 必填约束。                            |
| event `occurred_at` 与当前服务时钟的允许偏差                            | Schema 只要求非负整数，不表达“最多未来 5 分钟” | HTTP ingest 入口 `services/collector/src/http.rs` 检查时间转换与未来偏移                                                            | 目前 canonical fixture 不覆盖时钟依赖边界；列入第六步 parity/语义补充。                                           |

## 现有证据与第六步缺口

已核对的基础证据：

- [第一步样本基线](m0b-step1-sample-baseline.md)：事件 11 valid / 17 invalid；policy 2 valid / 8 invalid，含纯 Schema、协议脚本和 Collector 判定结果及现存缺口。
- [第三步生成类型质量报告](m0b-step3-generated-type-quality.md)：TS 编译/类型探针；typify Serde policy fixture 与变异探针，记录空 origins、重复 origins、schema_version 和整数宽度差异。
- 事件规则的具体 canonical fixtures 位于 `protocol/events/fixtures/{valid,invalid}/`；policy fixtures 位于 `protocol/contracts/configuration/current/fixtures/environment-policy/{valid,invalid}/`。
- Collector 事件验证：`services/collector/src/validation.rs`；Custom Event runtime constraints：`services/collector/src/protocol.rs`；配置策略解析：`services/collector/src/runtime_policy.rs`；策略 registry 冲突：`services/collector/src/config.rs`。

第六步优先补充或单独定义 parity cases：事件标识符与 URL/date-time 边界、batch 100 项边界、Context 数值边界与闭合未知字段、Custom properties 全部大小/类型边界、Web Vital Page View 时间先后关系、policy 无效 date-time 与 format assertion、未知字段和 schema_version 变异、空/重复 Origin、整数超范围差异、数据库行身份不匹配及未来时间窗口边界。跨文档/时钟/隐私语义用独立语义测试，不伪装成纯 Schema fixtures。

## 本步结论

Schema 负责可机器表达的 wire 结构和部分格式/范围，但 TypeScript/Rust 声明不能完整表达并自动验证这些输入约束。json2ts/typify 生成结果也存在已实测的语义差异。运行时应保留 Schema 校验与显式语义校验；生成类型不能代替对不可信 JSON 的验证。Custom Event 隐私/资源限制、Web Vital 评分与事件关系、batch 单站点、策略数据库身份及跨策略 Origin 冲突有各自的运行时所有者，必须在 parity 工作中与 Schema 判定分栏记录。
