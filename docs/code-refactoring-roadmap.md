执行状态和分组任务见 [代码重构执行 Checklist](./code-refactoring-checklist.md)。

工作包 1 的基线评审已完成。候选顺序保持不变；首个完整切片仍为 [Dashboard 创建站点向导试点设计](./code-refactoring-site-creation-pilot.md)，下一项实施任务是工作包 2（Dashboard 创建站点流程）。试点文档定义了职责边界、测试缺口、验收和可分开的审查/回退边界；实现前仍须按基线核实相关动态行为。

后续每个工作包开始实现前，应根据其实际调用链细化为可单独审查和回退的变更边界，并确认关联测试与失败诊断覆盖；路线图当前定义的是领域工作包层级，尚未替后续工作包预先确定文件级拆分。

## 目标

降低高复杂度模块的阅读和修改成本，让展示、业务流程、I/O、领域规则和验证职责有清楚的边界。重构期间保持对外行为、HTTP/API 契约、数据库结构和 E2E 覆盖不变；需要改变行为时，另立功能任务和设计决策。

文件行数用于发现候选，不作为拆分验收标准。一个职责清晰的 250 行模块可能比几个互相跳转的 80 行文件更容易维护。重点检查职责数量、依赖方向、状态所有权、重复逻辑和测试隔离能力。

## 设计约定

### 前端：按状态所有权拆分 Container 和 Presenter

- Container 或领域 hook 持有异步请求、加载/提交状态、表单状态、路由参数和用户动作；它把可展示的数据和回调传给视图。
- Presenter 接收明确的 props，负责语义化标记、布局和局部交互呈现，不直接调用 API、不解析 URL、不维护远程缓存。
- 纯转换、校验和领域计算移入相邻的 `lib/<domain>/` 或组件域模块，并尽量保持无副作用，便于单元测试。
- 一个 Presenter 可以由多个按用户流程划分的视图组件组成，例如向导步骤、定义编辑区域、确认对话框和反馈状态。避免按 JSX 标签种类拆文件。
- 只有在状态共享或复杂度足以形成稳定边界时才抽 hook；不为遵循模式而给每个简单组件增加一层 Container。
- 组件域内测试展示状态和用户动作；领域逻辑的纯函数测试放在逻辑模块旁；API client 继续在其自身边界测试请求/响应处理。

建议先从 `site-creation-wizard.tsx` 做垂直切片：盘点创建、配置初始化、依赖选择、替换/重试等用户流程；确定谁拥有各状态后，先抽纯函数和 API 操作，再拆步骤视图，最后让顶层组件只保留流程编排。接着用相同判断方式处理定义、配置和 ingest key 管理器，不预设它们必须有相同文件结构。

### Rust：lib.rs 做模块入口，围绕领域能力和类型组织

- crate 的 `lib.rs` 保持模块声明、公开类型/API 汇总和少量 crate 级组装逻辑；具体运行时实现放入具名子模块。
- 以领域行为作为第一层模块边界，例如配置快照、schema 验证、运行时更新/读取、HTTP ingest、身份/密钥验证、策略解析、配置版本读写。
- struct/enum/trait 与其不变量、主要方法和紧密耦合的私有辅助代码放在同一模块。跨领域编排放在服务或 use-case 模块，不把领域规则塞进 HTTP handler。
- 依赖方向保持单向：传输入口调用应用服务；应用服务依赖领域接口；存储实现负责 SQL/数据库映射。避免循环模块依赖和仅为缩短文件而过度抽象 trait。
- 先移动代码并保持函数签名和行为，再独立评估是否需要改变可见性/API。私有实现优先，不扩大 crate 的公共 API。
- 测试优先靠近被测模块。大型集成测试可按 HTTP 路由、配置/站点管理、写入/查询等场景分模块，并共用少量明确的 fixture/helper；不要把大量断言搬进通用测试框架。

`configuration-runtime/lib.rs` 是适合的低风险试点：检查 `CapabilitySnapshot`、`CapabilitySchemaValidator` 和 `CapabilityRuntime` 的职责及共享不变量，将实现移入围绕这些概念命名的子模块；`lib.rs` 负责导出需要的公共类型。随后按请求边界处理 Collector `http.rs`，再处理 Analytics API 的 configuration store/service 边界。`processor.rs` 应先画出处理步骤及其数据所有权，再决定按 normalize、aggregate、dimension 等实际阶段拆分，不能仅根据函数长度猜模块。

### Tooling、E2E 和其他文件：薄入口，职责模块化

- 命令入口保留参数解析、依赖注入和顶层退出码；可复用实现放在有明确领域名称的模块中。
- 契约 validator 可按合同域拆成结构加载、语义规则和诊断输出，但拆分后应继续提供原有 package 命令及退出码。
- E2E 每个 suite 保留可识别的 suite 入口和场景意图；将场景按用户流程拆分为模块，公共造数、HTTP/数据库辅助和环境生命周期复用 `tests/e2e/support` 与现有 runner。失败时的截图、日志、诊断和清理行为必须保持。
- Shell 文件应主要做参数校验和调用实际实现；复杂逻辑应放到适合的 JS/Rust 工具模块。数据库迁移测试的大型脚本要先明确 shell 与 Rust 测试职责，避免重复实现同一组断言。
- HTTP 集成测试按 endpoint/能力域拆场景；CSS 按 dashboard shell、表格、表单等实际组件域拆分前，检查全局样式顺序、选择器冲突和 Next.js 的加载规则。

## 推进阶段

### 阶段 0：建立基线和拆分设计

1. 重新扫描受版本控制的源文件，标注生产代码、测试、生成文件、实验代码和迁移/fixture；每个候选记录职责、主要调用方、状态/数据流、已有测试和风险。
2. 对每个候选画一页以内的依赖/流程草图，回答：入口是什么、状态由谁持有、哪些逻辑有副作用、哪些不变量必须一起修改、哪些部分可独立测试。
3. 记录当前相关检查命令和结果。按仓库要求选择 dashboard 检查、`pnpm check`、Rust fmt/clippy/test/build、目标 suite E2E；大改动前后用相同命令比较。
4. 将每个高优先级候选拆成独立、可审查的 PR/提交，每个改动聚焦一个边界；先排清晰且测试完整的模块，不按最大行数机械排序。

**完成标准：** 有候选清单、依赖图、测试基线、拆分草图及可逐个合并的工作项；没有开始跨全仓的大规模搬移。

### 阶段 1：Dashboard 组件试点

1. 选 `site-creation-wizard.tsx`。列出加载、输入、提交、失败重试、重复提交/替换标记、能力初始化等状态迁移和 API 调用。
2. 将纯输入派生/规则函数放到 domain helper；为关键状态迁移和边界条件补测试（仅在现有覆盖不足时）。
3. 提取远程操作或流程状态到相邻 hook/container；Presenter 通过 props 接收视图数据和动作。
4. 按用户步骤拆视图，并明确 loading、error、empty、success 状态；保留可访问性和现有交互。
5. 用同一拆分准则审查 `definition-editor`、`configuration-editor`、`ingest-keys-manager`，逐个推进。避免将所有表单统统放进一个通用表单框架。

**完成标准：** 组件顶层能快速看出页面流程；请求与展示职责清晰；已有用户行为和错误状态有测试覆盖；Dashboard 的类型检查/测试/构建通过。

### 阶段 2：Rust 模块试点与服务边界

1. 先整理 `configuration-runtime/lib.rs`：把实现移入概念明确的模块，重导出稳定 API，收窄非必要可见性。
2. 整理 Collector `http.rs`：路由声明、请求/响应类型、输入提取与错误映射、应用流程调用分开；通用鉴权/限流/策略逻辑留在现有领域模块或合理的新模块。
3. 审查 Analytics API 的 `configuration.rs` 与 `config_store.rs`：区分 handler/use-case、配置校验/兼容转换、数据库读写；不要让 service 和 store 重复做校验。
4. 审查 `processor.rs`：按实际处理流水线拆分内部步骤和数据类型，保留处理顺序、不变量、事务范围和重建语义。
5. 对大型 Rust 测试按行为场景拆开，保留公共 fixture 的简单显式接口；测试名称继续表达领域行为。

**完成标准：** crate 入口只暴露/组装；领域边界可从目录和类型名看懂；公共 API 和数据库行为不变；workspace fmt、clippy、test、build 通过。

### 阶段 3：E2E 和契约 tooling 模块化

1. 以 `e2e-dashboard.mjs` 为首个候选，按 dashboard 运行时、导航/指标、受众维度、定义管理、API 错误等场景划分文件；先确定 suite 入口怎样调用场景，再搬移实现。
2. 检查 `e2e-analytics.mjs`、`e2e-configuration.mjs` 是否需要同类场景分组；只抽多个 suite 确实共有的机制，不把单一业务断言做成泛化工具。
3. 拆契约 validator 时按 schema/合同边界组织规则，把文件读取和报告输出做成薄适配层；保留当前 CLI、错误路径和 package script 入口。
4. 检查迁移测试 shell 与 Rust 测试的职责重叠，并决定由一个稳定入口编排的目标结构；迁移历史 SQL 不改写。

**完成标准：** 一个 suite/validator 的入口易读；场景逻辑有领域名称且没有循环依赖；失败诊断、suite 清理、CLI 行为保持；相关 E2E/契约命令通过。

### 阶段 4：按证据处理剩余大文件

1. 复查 HTTP/Processor 集成测试、styles.css、API client 和其余超过 200 行的文件。
2. 只有当职责、依赖或修改冲突确实形成边界时才拆；CSS 应按视觉组件/区域定义导入方案，测试应按行为组拆，不只按行数切片。
3. 归档候选决策：拆分、保持现状并记录原因、或转入后续功能工作。生成文件/实验产物通常不列入生产重构排期。

**完成标准：** 每个活跃候选有明确处理结论；没有仅为达成行数指标而制造的模块。

### 阶段 5：回顾和约束

1. 复核目录命名和模块导出，删除搬移后无人使用的 helper、旧路径和重复测试。
2. 比较重构前后的调用链、测试可定位性、局部变更范围和新人阅读路径。若文件更短但跳转更多、职责边界更模糊，应调整设计。
3. 更新本计划中的状态和实际结构；只有在形成长期架构规则时，才新增/更新 ADR。重构本身不需要为了记流水账新增 ADR。

## 每个工作项的执行方法

1. **理解：** 阅读整个目标文件、直接调用方、相邻类型、配置/协议及相关测试；写下行为清单和明确不变量。
2. **划界：** 给每个函数/类型标注职责、I/O 和状态所有者，按概念与变更理由分组；画出允许的依赖方向。
3. **保护行为：** 运行相关现有检查并找覆盖空洞。仅为现有行为加最小的特征测试，避免在结构搬移同时改产品行为。
4. **小步移动：** 一次抽一个纯逻辑/视图/领域职责，修正 imports 和可见性，保持每一步可编译、可格式化、可审查。
5. **清理入口：** 移除已搬走的实现，确保入口仅做编排；不要保留重复实现或兼容层，除非确实有外部调用者依赖。
6. **验证：** 运行目标模块测试和仓库规定的检查；对 E2E/HTTP/数据库边界运行对应集成验证。记录未能运行的验证及原因。
7. **审查：** 看最终 diff 是否只有结构变化、行为断言是否保留、模块边界是否减少跨文件耦合，再提交一个主题明确的变更。

## 风险控制与完成定义

- 按一个领域边界一个改动批次推进；大型 Processor 或 HTTP 测试拆分可再分数个独立提交。
- 结构搬移期间避免协议、SQL schema、迁移内容、业务规则、视觉设计和错误语义变化。
- 异步/副作用代码的移动要覆盖取消、重试、重复提交、超时、部分失败及清理语义（适用时）。
- 重构完成不以“所有文件低于 200 行”衡量。验收看职责边界是否清楚、依赖是否单向、测试是否能定位失败，以及常见修改是否只需触及相关模块。
- 单个工作项只有在实现、相关自动化检查、必要文档和端到端路径都完成后才关闭；若验证受环境限制，明确标记剩余验证。
