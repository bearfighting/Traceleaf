# M5 Site Management Backend Checklist

- Status: In progress; M5.1 contract freeze complete; M5.2 Site directory and lifecycle APIs implemented
- Prerequisites: M1 module boundaries, M3 Site Registry, and M4 local runtime-authority cutover; ADR-013 and ADR-014 accepted
- Related: [Platform improvement roadmap](platform-improvement-roadmap.md), [Site Onboarding and Settings Design](site-onboarding-settings-design.md), [Analytics and Site Management Module Boundaries](analytics-site-management-module-boundaries.md), [ADR-013](decisions/ADR-013-site-identity-and-lifecycle.md), [ADR-014](decisions/ADR-014-runtime-configuration-authority.md)

## Goal and scope

Deliver the Site Management backend workflow for listing, reading, creating, updating metadata and archiving/restoring Sites. A new Site must be created with the minimum configuration needed to receive events, without leaving partial state if any operation fails. Existing configuration APIs remain supported and keep owning their independent updates.

M5 is backend-only. The Dashboard onboarding flow and removal of the automatic local development seed belong to M6. Do not add team management, RBAC, public management access, URL reachability probes, domain-ownership verification, or physical Site deletion in M5.

## Frozen behavior

- Site IDs are generated by Site Management, stable, and unrelated to display name or Website URL. Names may repeat; Website URL is mutable metadata.
- Creating a Site requires a non-empty display name, a valid HTTP(S) Website URL, and one explicit environment. `production` may be the client/UI suggested value, but the API and stored policy must carry the explicit environment.
- New Sites enable required Page Views only by default; other capabilities start disabled. Existing Sites retain their current configuration and history.
- The first environment policy is enabled with the existing 600 requests/minute default, and the generated Ingest Key is active; ingestion is ready after runtime application.
- The create transaction writes Registry metadata, capabilities, activation windows, the first environment policy, an Ingest Key digest and ID, the idempotency association, and audit data atomically.
- The database stores no recoverable plaintext Ingest Key. Return it only in the first successful create response. A same-key/same-request retry returns Site metadata without the key; same key with a different normalized request returns conflict. Keep the request association for the Site lifetime, including after archive; never reuse that Site ID.
- Archive blocks new ingestion while preserving historical analytics, configuration, key digests and audit. Restore does not enable an environment policy automatically. M5 does not physically delete Sites.
- Site Management owns writes. Analytics and runtime services continue using their existing read paths and configuration contracts; Site Management does not write analytics facts.
- Management routes remain protected by deployment-admin authorization. Dashboard must not access PostgreSQL directly.

## Execution checklist

### M5.1 — Freeze the API and persistence contract

- [x] Define request/response schemas, endpoint methods, validation rules, error envelope, status codes, ETag/version behavior, and idempotency header semantics before implementation.
- [x] Define canonical request normalization and digest inputs; exclude the idempotency key itself and never include generated secrets in the digest or logs.
- [x] Define additive persistence for request ID, normalized request digest and Site association, including uniqueness/concurrency guarantees and lifetime retention.
- [x] Extend the audit contract for Site creation, metadata changes, archive and restore without recording plaintext keys or other secrets.
- [x] Add API contract fixtures and document the creation/retry/key-recovery behavior.

**Exit:** API and persistence contracts are reviewed, versioned and testable before handlers are implemented.

### M5.2 — Implement the Site Management module and directory APIs

- [x] Keep routes, handlers, services, repositories, models and errors inside the Site Management module; let the application layer compose routers only.
- [x] Implement authenticated Site list and detail reads, including lifecycle, derived setup status and missing setup requirements.
- [x] Implement metadata update and archive/restore operations with validation, version/concurrency protection, and audit records.
- [ ] Preserve Registry-only historical Sites and existing analytics/configuration API behavior.
- [ ] Add module-boundary and HTTP contract tests for authorization, validation, not-found, conflict and database failures.

Runtime application state is intentionally not duplicated in the Site directory response. Management clients read effective capability application state from the capabilities endpoint and effective ingest-policy state from the corresponding environment policy endpoint; those contracts remain authoritative for their independent configuration versions. `setup_status` and `missing_requirements` describe stored onboarding readiness only; every enabled environment must have origins and an active key for the Site to be ready.

**Exit:** Administrators can inspect and maintain Site metadata/lifecycle through the management API; no direct database access or cross-domain repository calls are introduced.

### M5.3 — Implement atomic Site creation and idempotency

- [ ] Generate a stable unique Site ID on the server; do not infer Website URL from an Allowed Origin.
- [ ] In one database transaction, insert the Site, default capabilities and activation windows, first environment policy, key digest/key ID, idempotency record and creation audit.
- [ ] Reuse existing capability, Origin and key validation rules rather than creating a second validation path.
- [ ] Enforce same idempotency key + same normalized request as a metadata-only replay, and same key + different request as conflict, including simultaneous requests.
- [ ] Return the plaintext key only after the first transaction commits successfully; provide replacement-key recovery after a lost response.
- [ ] Prove transaction rollback leaves no Registry, capability, activation, policy, key, audit or idempotency fragments after any injected failure.

**Exit:** A successful create can ingest an event immediately; retries cannot duplicate the Site or reveal the original key again; failures leave no partial Site.

### M5.4 — End-to-end verification and closeout

- [ ] Add PostgreSQL integration coverage for create, list/detail, metadata changes, archive/restore, audit, rollback, idempotent replay, conflicting replay and concurrent duplicate requests.
- [ ] Verify a newly created Site can accept an event through Collector and produce Analytics data through Processor; verify archive rejects new events and historical reports remain available.
- [ ] Verify current configuration APIs and runtime-state reporting still work for existing and newly created Sites.
- [ ] Run unit, integration, contract, formatting, type-check, build and relevant E2E commands through the documented scripts/CI equivalents.
- [ ] Update this checklist, roadmap, operational documentation and any changed ADR with implementation and validation evidence.

**M5 exit:** An administrator can list and inspect Sites, create a fully configured Site atomically, update metadata, and archive/restore it; audit and idempotency guarantees hold under retries and concurrency; the new Site works end to end without breaking historical analytics or existing configuration APIs.
