# M4.3 Definitions Import Closeout

**Target:** local development database only  
**Date:** 2026-10-01  
**Status:** Complete for local development. Database evidence is carried forward from the M4.1 import because M4.3 performs no local target data writes.

## Change

The Processor's normal Compose service no longer receives `ANALYTICS_DEFINITIONS_FILE`, and `.env.example` no longer suggests that definitions files are regular Processor configuration. The Processor continues to read the variable only when the operator explicitly supplies `--import-definitions-if-empty`. The existing default file path remains `config/analytics-definitions.json` relative to the Processor working directory.

The ordinary `--once` integration scenario supplies a nonexistent file path and verifies that processing succeeds without creating a definition revision or import audit record. The explicit importer retains its existing integration coverage for first import and idempotent repeat behavior.

## Explicit legacy import operation

After the database is migrated and required Site capability configuration exists, invoke:

```sh
docker compose --profile processing run --rm --no-deps --entrypoint cargo processor run -p processor -- --import-definitions-if-empty
```

The default file is available through the Processor's `/workspace` project mount. To import a different file, add a command-scoped environment override:

```sh
docker compose --profile processing run --rm --no-deps -e ANALYTICS_DEFINITIONS_FILE=/workspace/path/to/file.json --entrypoint cargo processor run -p processor -- --import-definitions-if-empty
```

`--no-deps` prevents Compose from launching db-migrate and the development seed. The operator must ensure the target database is already migrated and ready. Import skips Sites that already have revisions and creates audit records for newly imported Sites.

## Local data evidence

M4.1 imported `config/analytics-definitions.json` once for `site_playground`: revision 1, source definition version `2026-09-23.1`, one Conversion, one Funnel and one audit record. A second explicit invocation imported zero Sites. The M4.1 evidence and backup records are listed in the [M4 runtime configuration authority checklist](m4-runtime-configuration-authority-checklist.md).

M4.3 does not repeat the importer against the local target. This avoids an unnecessary database write; the stored revision and audit evidence remain as recorded during M4.1. Other deployment targets require their own inventory and verification before retiring their definitions-file path.

The new ordinary-processing CLI scenario and the existing explicit-import idempotency scenario both passed against a separate temporary PostgreSQL 18.6 database. The temporary database was stopped after the checks. Rust formatting, Processor integration-test compilation, documentation formatting and `git diff --check` passed. The existing M4.1 local target inventory remains the read-only evidence for the preserved revision and audit record.

## Acceptance

- Regular Processor Compose configuration and `.env.example` do not wire the definitions file.
- Ordinary Processor processing does not inspect the path even when `ANALYTICS_DEFINITIONS_FILE` is set to an invalid location.
- Definitions remain available through the explicit, idempotent migration command.
- Existing local revision and audit history is preserved; this stage does not switch runtime authority.
