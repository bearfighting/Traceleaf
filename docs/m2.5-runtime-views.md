# M2.5 Runtime Views and Capability Registry

## Runtime boundary

Stored policy and capability documents remain validated by their existing JSON Schemas before the runtime views are built. HTTP management updates also retain their current Schema and service-rule checks. The API validates policy and capability JSONB documents before projecting them into existing response bodies; invalid stored documents return the established `configuration_unavailable` response. Collector retains its last-good policy and marks it stale when a stored document fails validation.

`configuration-runtime` now owns the shared runtime view types:

- `EnvironmentPolicyView` contains the site/environment identity, schema version, configuration version, enabled state, Origins, rate limit, timestamp strings, and ingest-key metadata. `parse_validated` checks the row identity and limits after the Collector's existing Schema check. Timestamps remain strings and the M2.4 date-time deployment gate remains open.
- `CapabilitySnapshot` is keyed by the shared `CapabilityId` enum. Its schema validator constructs the Registry once at service startup, then snapshot parsing checks the storage row and enabled dependencies from the Registry.
- `DefinitionRevisionView` checks server metadata and row identity for Processor reads/rebuilds and Analytics current-definition reads. Processor then applies its existing `AnalyticsDefinitions::validate` rules. Definition version metadata follows that validator’s nonblank, 64-character limit for both stored revision views and Analytics revision listings. Legacy import continues to default omitted `active` flags to `true` before persisting the document. There is no stored revision JSON Schema.

## Capability Registry

`protocol/capabilities/capabilities.json` remains the canonical manifest. `configuration-runtime::CapabilityRegistry` reads it at startup and validates the manifest Schema, supported schema version, the complete ID set, duplicates, dependency references, dependency cycles, and planned capability surface restrictions. Runtime behavior fields are limited to ID, status, and dependencies. Description fields remain in the manifest. The Registry's Rust tests compare its compiled ID set to the canonical manifest and reject invalid registry cases. Both management updates and stored capability snapshots reject enabled capabilities whose Registry status is `planned`. `pnpm capabilities:validate` checks the protocol manifest in CI.

Processor retains its compatibility re-exports for `CapabilityId`, `CapabilityRegistry`, and `CapabilityStatus`. The existing `CapabilityContract` description-shaped type remains available to avoid removing its public type path; service decisions use the shared Registry.

## Consumer map

| Consumer                            | Runtime view and boundary                                                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Collector                           | Shared `EnvironmentPolicyView`; existing stored-policy Schema check remains first; last-good/stale behavior remains in `RuntimePolicyManager`.         |
| Collector, Processor, Analytics API | Shared capability Registry and `CapabilitySnapshot`; capability IDs/dependencies no longer come from duplicated service lists.                         |
| Processor                           | Shared `DefinitionRevisionView`; validates database row metadata, then validates projected definitions with `AnalyticsDefinitions`.                    |
| Analytics API                       | Shared policy/revision views; stored policy, capability and definition-set GET paths validate stored content before returning current response shapes. |

## Compatibility and deferred work

No JSON Schema, database document format, HTTP response shape, ETag behavior, or production Schema-validation boundary changed. Definition imports preserve their `active: true` default. Strict timestamp validation remains disabled until the M2.4 preflight has passed for both configuration tables in every deployment and remediation is recorded. Static runtime views supplement the runtime Schema checks; they do not replace them under ADR-015.

Site Registry and Site creation work remain outside M2.5.
