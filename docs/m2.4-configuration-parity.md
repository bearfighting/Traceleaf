- Status: implementation in progress; deployment date-time gate is open.
- Scope: Stored Environment Policy V1, Stored Site Capabilities V1, three configuration update contracts, stored definition revisions, and Processor's legacy definition import.
- Runner: `node scripts/m2-configuration-parity.mjs` checks canonical Schema fixtures and strict date-time candidates. It does not claim runtime TS parsing: generated TS declarations are compile-time shapes. Rust and service outcomes are additionally covered by the named consumer tests below.

## Explicit rules and known gaps

- Policy `schema_version == 1`, non-empty origins and uniqueness are not supplied by Typify/Serde alone. Collector currently gets origin cardinality, regex, uniqueness and unknown-field rejection from the startup-built Schema validator; its parser checks version and row identity. These remain independently asserted in consumer tests so generated structure success is not treated as full validation.
- Capabilities identity, storage version, required Page Views and dependencies are consumer semantics. Unknown fields and fixed privacy constants are Schema/Serde boundary behavior; fixtures should keep testing them through the runtime.
- Update Origin normalization, dependencies, duplicate definition IDs, privacy field filtering and HTTP error mapping are service semantics, not type constraints. Keep their outcome assertions in Analytics API tests.
- TypeScript types are not runtime parsers. Positive and `@ts-expect-error` probes establish static shape only. Schema fixtures and Rust/HTTP consumers establish runtime behavior.
- Policy `version` and `rate_limit_per_minute` have no Schema upper bound, while Collector and PostgreSQL BIGINT paths are signed 64-bit. Values above `i64::MAX` are an implementation-range exception; this report does not tighten Schema or claim full parity. JavaScript `number` also cannot represent every large JSON integer exactly.
- Definition revisions have no direct stored-document Schema. The update contract and Processor import path are separate inputs with server-managed revision metadata; parity is limited to shared semantic expectations and currently named fixtures.

## Date-time compatibility gate

The strict candidates are policy `/updated_at`, every `/ingest_keys/*/created_at`, and capability `/updated_at`. Existing production validators keep their current format behavior. The read-only preflight now covers both `site_environment_policies` and `site_capability_configurations`; its `--fixtures` mode exercises policy timestamps and the capability `updated_at` candidate. No deployment results are recorded here. Strict format assertions must not be enabled or released until this preflight has run against both tables in every deployment and remediation is recorded. Preserve last-good/stale behavior for invalid stored policy documents.

Canonical candidates:

- `environment-policy/invalid/invalid-updated-at-date-time.json`
- `environment-policy/invalid/invalid-key-created-at-date-time.json`
- `capabilities/invalid/invalid-updated-at-date-time.json`

Run `node scripts/audit-policy-datetimes.mjs --fixtures` to check both stored document types; run the same command without arguments with an explicit deployment `DATABASE_URL` for the read-only database audit. The candidate Schema outcomes are exercised by `node scripts/m2-configuration-parity.mjs`; production acceptance remains governed by existing Collector/configuration-runtime tests until the deployment gate closes.

This assessment does not declare M2.4 complete. Per-deployment database runs, exhaustive TS type probes and the full per-fixture cross-consumer result matrix remain required before exit; strict date-time activation remains a release gate.

## Database-mode preflight exercise

The modified database path was exercised against a disposable PostgreSQL 18.6 container using tmpfs storage and minimal tables with the required columns. The invalid-data run reported the policy `/updated_at`, policy `/ingest_keys/0/created_at`, and capability `/updated_at` field paths without printing timestamp values. The valid-data run reported all policy and capability timestamps valid. Both tables retained their two seeded rows after the audit. The database and credentials were test-only; no deployment database was accessed.
